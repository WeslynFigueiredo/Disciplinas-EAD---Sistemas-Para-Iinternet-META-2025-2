💳 O Que São Transações? - A Unidade de Trabalho

Definição
Uma Transação é uma sequência lógica de operações de banco de dados que é tratada como uma UNIDADE ÚNICA E INDIVISÍVEL de trabalho.
🚂
Analogia - O Trem nas Montanhas
Imagine um trem de carga atravessando um túnel na montanha. O trem INTEIRO deve atravessar ou NENHUM vagão entra. Não faz sentido 'metade do trem' atravessar!
Características:
  • Agrupa múltiplas operações SQL
  • Tratada como um único bloco
  • Ou todas as operações acontecem (COMMIT)
  • Ou nenhuma acontece (ROLLBACK)
Sintaxe Básica:
BEGIN TRANSACTION;

-- Operação 1
UPDATE contas SET saldo = saldo - 100 WHERE id = 1;

-- Operação 2
UPDATE contas SET saldo = saldo + 100 WHERE id = 2;

COMMIT; -- Confirma tudo
-- ou ROLLBACK; -- Desfaz tudo

🏦 Exemplo Clássico: Transferência Bancária

Cenário
Maria quer transferir R$ 500,00 da sua conta para a conta de João.
Operações Necessárias:
BEGIN TRANSACTION;

-- Operação 1: Retirar R$ 500 da conta de Maria
UPDATE contas 
SET saldo = saldo - 500 
WHERE titular = 'Maria';

-- Operação 2: Adicionar R$ 500 na conta de João
UPDATE contas 
SET saldo = saldo + 500 
WHERE titular = 'João';

COMMIT;
Por Que É Uma Transação?
Se APENAS a Operação 1 acontecer (retirar de Maria) mas a Operação 2 FALHAR (não adicionar em João), o dinheiro DESAPARECE do sistema! R$ 500 evaporam!
Solução com Transação:

✅ Se AMBAS operações funcionarem → COMMIT (confirma tudo)

❌ Se QUALQUER operação falhar → ROLLBACK (desfaz tudo, Maria continua com o dinheiro)

Resultado: Transações garantem que o sistema NUNCA fique em estado inconsistente (dinheiro perdido ou duplicado).

🔐 ACID - Os 4 Pilares da Confiabilidade

O Que É ACID?
ACID é um acrônimo que representa as 4 propriedades fundamentais que garantem a CONFIABILIDADE de transações em bancos de dados.
Os 4 Pilares
A
Atomicidade
Tudo ou Nada
C
Consistência
Sempre Válido
I
Isolamento
Sem Interferência
D
Durabilidade
Permanente e Seguro
Por Que ACID É Importante?
Sem ACID, sistemas críticos (bancos, hospitais, e-commerce) seriam totalmente inseguros. Dados poderiam ser perdidos, corrompidos ou inconsistentes.

⚛️ Atomicidade (A) - Tudo ou Nada

Definição
Uma transação é ATÔMICA se ela é completada TOTALMENTE (COMMIT) ou DESFEITA TOTALMENTE (ROLLBACK). Não existe 'meio-termo'.
✈️
Analogia - Comprar um Pacote de Viagem
Você compra um pacote: passagem + hotel + passeios. Se o HOTEL não estiver disponível, você NÃO quer apenas a passagem. Você quer CANCELAR TUDO ou TER TUDO.
Exemplo - Transferência:
BEGIN TRANSACTION;

UPDATE contas SET saldo = saldo - 500 WHERE id = 1;
UPDATE contas SET saldo = saldo + 500 WHERE id = 2;

COMMIT; -- ✅ Ambas operações confirmadas

-- Se houver erro:
ROLLBACK; -- ❌ NENHUMA operação é mantida
Comandos ACID:
  • COMMIT: Confirma todas as operações da transação (salva definitivamente)
  • ROLLBACK: Desfaz todas as operações da transação (volta ao estado inicial)
Garantia da Atomicidade:
✅ Ou a transferência COMPLETA acontece (ambas atualizações)
❌ Ou NADA acontece (como se nunca tivesse começado)

✅ Consistência (C) - Sempre Válido

Definição
Uma transação leva o banco de dados de um ESTADO VÁLIDO para outro ESTADO VÁLIDO, respeitando TODAS as regras e restrições (constraints, foreign keys, checks).
🧩
Analogia - Quebra-Cabeça
Imagine um quebra-cabeça montado (estado válido). Você pode mover algumas peças durante a montagem, mas no FINAL, o quebra-cabeça deve estar COMPLETO e CORRETO novamente. Estados intermediários 'bagunçados' não são visíveis para outros.
📋 Regras Que Devem Ser Respeitadas
  • Chaves primárias únicas
  • Foreign keys válidas
  • Checks (ex: saldo >= 0)
  • Triggers e constraints personalizadas
❌ Exemplo - Violação de Consistência
-- ANTES: Conta A tem saldo = 200

BEGIN TRANSACTION;
UPDATE contas SET saldo = saldo - 500 WHERE id = 'A';
-- VIOLAÇÃO: saldo ficaria negativo (-300)!

ROLLBACK; -- Sistema detecta e DESFAZ
✅ Garantia da Consistência
O SGBD NUNCA permite que uma transação deixe o banco em estado INVÁLIDO. Se uma regra for violada, a transação é REJEITADA (ROLLBACK automático).

🔒 Isolamento (I) - Sem Interferência

Definição
Transações SIMULTÂNEAS (concorrentes) devem ser executadas como se fossem ISOLADAS umas das outras. Uma transação NÃO pode ver os estados intermediários de outra.
🚪
Analogia - Cabines de Votação
Imagine cabines de votação. Cada pessoa vota em PRIVADO (isolada). Ninguém vê o voto dos outros durante o processo. Só no FINAL (após COMMIT) os votos são contabilizados juntos.
⚠️ Problema Sem Isolamento

Transação A: Lê saldo = 1000, calcula novo saldo = 900

Transação B: Lê saldo = 1000 (ainda não viu mudança de A), calcula novo saldo = 800

Resultado: Apenas a última atualização sobrevive. PERDA DE ATUALIZAÇÃO!

🔐 Solução: Locks (Travas)

O sistema usa locks para garantir que quando A está modificando um registro, B deve ESPERAR até A terminar (COMMIT ou ROLLBACK).

✅ Garantia do Isolamento
Transações concorrentes não interferem. Resultado final = como se fossem executadas uma de cada vez (serialização).

💾 Durabilidade (D) - Permanente

Definição
Após uma transação ser CONFIRMADA (COMMIT), suas mudanças são PERMANENTES e SOBREVIVEM a qualquer falha (queda de energia, crash do sistema, etc.).
🪨
Analogia - Escultura em Pedra
Quando você termina de esculpir uma estátua de pedra (COMMIT), a obra está PERMANENTE. Mesmo que chova, faça sol, ou haja terremoto, a escultura permanece. Diferente de desenho na areia (dados em memória RAM - temporários).
🛡️ Como é Garantida?
  • Log de Transações: Todas as operações são gravadas em um arquivo de log ANTES de serem aplicadas
  • Write-Ahead Logging (WAL): Log é gravado no disco ANTES do COMMIT
  • Backup Periódico: Cópias de segurança regulares
  • Replicação: Dados copiados para múltiplos servidores
💡 Exemplo
BEGIN TRANSACTION;
INSERT INTO clientes VALUES (100, 'João Silva');
COMMIT; -- ✅ Gravado permanentemente no disco

-- 5 segundos depois: FALTA DE ENERGIA!
-- Quando sistema volta: João Silva AINDA EXISTE no banco!
✅ Garantia da Durabilidade
Após COMMIT, os dados NUNCA são perdidos, mesmo em caso de falhas catastróficas.

🔄 Concorrência - O Problema

O Que É Concorrência?
Quando MÚLTIPLAS transações tentam acessar e modificar os MESMOS dados AO MESMO TEMPO.
⚠️ Problemas de Concorrência

1. Leitura Suja (Dirty Read)

Transação A lê dados que Transação B modificou mas ainda NÃO confirmou (COMMIT). Se B fizer ROLLBACK, A leu dados INVÁLIDOS.

2. Leitura Não-Repetível (Non-Repeatable Read)

Transação A lê um dado. Transação B modifica e confirma. A lê novamente e vê valor DIFERENTE.

3. Leitura Fantasma (Phantom Read)

Transação A busca registros. Transação B insere novos. A busca novamente e vê registros NOVOS que não existiam antes.

4. Perda de Atualização (Lost Update)

Duas transações leem o mesmo valor, modificam e salvam. A última sobrescreve a primeira, causando PERDA DE DADOS.

👻 Leitura Suja - Exemplo Detalhado

Cenário: Reserva de Passagem Aérea

Situação Inicial: Voo XYZ tem 1 assento disponível.

📅 Linha do Tempo
Tempo Transação A (Maria) Transação B (João)
T1 BEGIN -
T2 UPDATE vagas SET disponivel = 0 -
T3 - SELECT disponivel (vê 0!) ❌
T4 ROLLBACK (erro no pagamento) -
T5 - Desiste (viu 0 vagas) 😢
❌ Problema
João viu dados NÃO-CONFIRMADOS (leitura suja). O assento na verdade estava disponível, mas ele desistiu baseado em informação FALSA.
✅ Solução: Isolamento com Locks
João seria BLOQUEADO de ler até Maria finalizar (COMMIT ou ROLLBACK).

🔐 Controle de Concorrência - Locks

O Que São Locks (Travas)?
Mecanismos que IMPEDEM que múltiplas transações acessem os mesmos dados simultaneamente de forma conflitante.
🔒 Tipos de Locks

1. Shared Lock (S) - Lock Compartilhado

Múltiplas transações podem LER o mesmo dado simultaneamente. Nenhuma pode MODIFICAR enquanto houver S-Lock.

2. Exclusive Lock (X) - Lock Exclusivo

Apenas UMA transação pode ter X-Lock. Ela pode LER e MODIFICAR. Outras transações devem ESPERAR.

⚙️ Como Funcionam?
Operação Lock Necessário Efeito
SELECT S-Lock Outros podem ler, ninguém pode modificar
UPDATE/DELETE X-Lock NINGUÉM pode ler ou modificar
INSERT X-Lock Lock na tabela/índice
🎯 Níveis de Isolamento SQL
  • READ UNCOMMITTED: Permite leitura suja
  • READ COMMITTED: Só lê dados confirmados
  • REPEATABLE READ: Leituras sempre retornam mesmo valor
  • SERIALIZABLE: Isolamento TOTAL (mais lento)

🔧 Recuperação - Log de Transações

O Que É o Log de Transações?
Um arquivo especial que registra TODAS as operações realizadas no banco de dados, ANTES de serem aplicadas. É a "caixa preta" do sistema.
📝 O Que É Registrado?
  • BEGIN TRANSACTION (início)
  • Operações: INSERT, UPDATE, DELETE
  • Valores ANTES e DEPOIS das modificações
  • COMMIT (confirmação)
  • ROLLBACK (cancelamento)
🛠️ Como a Recuperação Funciona?

1. Após Crash do Sistema

O SGBD lê o log e identifica transações que fizeram COMMIT antes do crash. Essas são REAPLICADAS (REDO).

2. Transações Incompletas

Transações que NÃO fizeram COMMIT são DESFEITAS (UNDO) usando os valores ANTES registrados no log.

📋 Exemplo de Log
[T1] BEGIN TRANSACTION
[T1] UPDATE contas SET saldo = 900 WHERE id = 1 (ANTES: 1000)
[T1] UPDATE contas SET saldo = 1100 WHERE id = 2 (ANTES: 1000)
[T1] COMMIT

-- CRASH DO SISTEMA AQUI! --

[Recuperação] T1 estava COMPLETA → REDO (reaplicar)

💾 Backup de Dados

Por Que Backup É Essencial?
O log de transações protege contra crashes, mas NÃO protege contra:
  • Exclusão acidental de dados
  • Corrupção de disco
  • Desastres naturais (incêndio, inundação)
  • Ataques de ransomware
🗂️ Tipos de Backup

1. Backup Completo (Full Backup)

Copia TODOS os dados do banco. Mais lento, mas recuperação é rápida.

2. Backup Incremental

Copia apenas as mudanças desde o ÚLTIMO backup. Rápido, mas recuperação é mais complexa.

3. Backup Diferencial

Copia mudanças desde o último backup COMPLETO. Meio-termo entre os dois anteriores.

⏰ Estratégia 3-2-1

3 cópias dos dados

2 tipos diferentes de mídia (HD, nuvem)

1 cópia em local EXTERNO (off-site)

🔄 Replicação vs Backup

Replicação: Cópia em TEMPO REAL para outro servidor. Protege contra falhas de hardware.

Backup: Cópia PERIÓDICA. Protege contra exclusão acidental e corrupção.

Ideal: Usar AMBOS!

📝 Atividade 5 - Aplicando ACID

Cenário: Sistema de Reserva de Passagens Aéreas

Você está desenvolvendo um sistema de reserva de passagens. O sistema deve:

  • Permitir que múltiplos usuários façam reservas simultaneamente
  • Garantir que o mesmo assento não seja vendido duas vezes
  • Manter a integridade dos dados mesmo em caso de falhas
  • Registrar todas as transações para auditoria
🎯 Tarefa

Para cada situação abaixo, identifique:

  1. Qual propriedade ACID está sendo aplicada?
  2. Por que essa propriedade é importante nesse contexto?
  3. O que aconteceria se essa propriedade NÃO fosse garantida?
📋 Situações para Análise

Situação 1: Durante uma reserva, o sistema debita o valor do cartão de crédito mas falha ao criar o registro da reserva. A transação é cancelada e o valor é estornado.

Situação 2: Dois usuários tentam reservar o último assento disponível ao mesmo tempo. O sistema garante que apenas um consiga completar a reserva.

Situação 3: Após confirmar uma reserva e exibir o bilhete eletrônico, ocorre uma queda de energia no data center. Quando o sistema volta, a reserva ainda existe e está válida.

📚 Resumo - Conceitos Fundamentais

🔐 Propriedades ACID
Propriedade Garantia Mecanismo
Atomicidade Tudo ou nada COMMIT / ROLLBACK
Consistência Sempre válido Constraints / Triggers
Isolamento Sem interferência Locks / Níveis de Isolamento
Durabilidade Permanente Log / Backup / Replicação
🔄 Problemas de Concorrência
  • Leitura Suja: Ler dados não confirmados
  • Leitura Não-Repetível: Valores mudam entre leituras
  • Leitura Fantasma: Novos registros aparecem
  • Perda de Atualização: Última modificação sobrescreve as anteriores
🛡️ Estratégias de Proteção
  • Log de Transações: Registra todas as operações (UNDO/REDO)
  • Backup Regular: Full, Incremental, Diferencial
  • Replicação: Cópias em tempo real
  • Locks: Shared (S) e Exclusive (X)
💡 Lembre-se
ACID não é apenas teoria - é o que torna bancos de dados CONFIÁVEIS para sistemas críticos (bancos, hospitais, aviação, e-commerce).
