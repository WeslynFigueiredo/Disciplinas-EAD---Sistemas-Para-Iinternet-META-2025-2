O que são Padrões de Projeto (Design Patterns)?

🎯

Padrões de Projeto são SOLUÇÕES ELEGANTES e REUTILIZÁVEIS para problemas RECORRENTES no design de software. São MODELOS/TEMPLATES, não códigos prontos.

Conceito-Chave

Padrões NÃO são código pronto! São ESTRATÉGIAS que você implementa.

Benefícios dos Padrões de Projeto
  • Vocabulário comum entre desenvolvedores
  • Aceleram o desenvolvimento (não reinventa a roda)
  • Facilitam comunicação na equipe
  • Código mais organizado e mantenível
  • Soluções testadas e comprovadas

Analogia: Receitas de Bolo vs Bolo Pronto

🎂 RECEITA DE BOLO (Padrão de Projeto)

  • É um MODELO/GUIA
  • Lista ingredientes e passos
  • Você IMPLEMENTA seguindo o guia
  • Pode adaptar ao seu contexto
  • Cada pessoa faz um bolo diferente seguindo a mesma receita

🍰 BOLO PRONTO (Código Pronto)

  • É o RESULTADO FINAL
  • Você consome diretamente
  • Não precisa fazer nada
  • Sem flexibilidade

Conclusão

Design Patterns são como RECEITAS. Você ainda precisa "cozinhar" (implementar), mas o caminho está traçado!

Classificação dos 23 Padrões GoF

3 Categorias Principais

1. CRIACIONAIS (5 padrões)

Foco: Criação de objetos

Problema que resolve: Como criar objetos de forma flexível?

Exemplos: Singleton, Factory Method, Abstract Factory, Builder, Prototype

2. ESTRUTURAIS (7 padrões)

Foco: Composição de classes e objetos

Problema que resolve: Como organizar classes e objetos em estruturas maiores?

Exemplos: Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy

3. COMPORTAMENTAIS (11 padrões)

Foco: Comunicação e responsabilidades entre objetos

Problema que resolve: Como objetos se comunicam e distribuem responsabilidades?

Exemplos: Observer, Strategy, Command, Iterator, Template Method, Chain of Responsibility, State, Visitor, Mediator, Memento, Interpreter

Entendendo Cada Categoria

CRIACIONAIS

Quando usar? Quando você precisa criar objetos de forma controlada e flexível

Benefício: Desacopla criação do uso

🏛️

ESTRUTURAIS

Quando usar? Quando você precisa compor objetos/classes em estruturas

Benefício: Facilita extensão e manutenção

Pensamento: "Como EU ORGANIZO objetos?"

💬

COMPORTAMENTAIS

Quando usar? Quando você precisa definir como objetos se comunicam

Benefício: Distribui responsabilidades de forma clara

Pensamento: "Como objetos SE COMUNICAM?"

Padrão Factory Method (Fábrica)

Padrão Criacional #1

🏭

Define uma INTERFACE para criar um objeto, mas DEIXA AS SUBCLASSES DECIDIREM qual classe instanciar.

Conceito-Chave

Você delega a decisão de QUAL objeto criar para as subclasses

Problema que Resolve

Quando você não sabe de antemão qual classe exata precisa instanciar, ou quando a criação varia conforme o contexto

Benefícios
  • Desacopla código cliente das classes concretas
  • Facilita extensão (adicionar novos tipos)
  • Centraliza lógica de criação

Analogia: Fábrica de Carros

FÁBRICA DE VEÍCULOS: Todas as linhas de montagem produzem VEÍCULOS. Cada linha decide qual TIPO de veículo produzir.

🚗

Linha 1: Fábrica de Carros de Passeio

Produz: Sedan, SUV, Hatchback

🚚

Linha 2: Fábrica de Caminhões

Produz: Caminhão leve, Caminhão pesado

🏍️

Linha 3: Fábrica de Motos

Produz: Moto esportiva, Moto custom

Conclusão

O CLIENTE pede "um veículo". A FÁBRICA (subclasse) decide qual TIPO criar. O cliente não precisa saber os detalhes!

Estrutura do Factory Method

CRIADOR (Classe Abstrata ou Interface)

+ factoryMethod(): Produto
+ operacao(): void {
    produto = factoryMethod()
    produto.usar()
}

CRIADOR CONCRETO A

+ factoryMethod(): Produto {
    return new ProdutoA()
}

CRIADOR CONCRETO B

+ factoryMethod(): Produto {
    return new ProdutoB()
}

PRODUTO (Interface)

+ usar(): void

PRODUTO A e PRODUTO B (Classes Concretas)

Exemplo Prático: Sistema de Pagamento

// Interface do Produto
interface Payment {
    processPayment(amount)
}

// Produtos Concretos
class CreditCardPayment implements Payment {
    processPayment(amount) {
        print "Processando $amount via Cartão de Crédito"
    }
}

class PayPalPayment implements Payment {
    processPayment(amount) {
        print "Processando $amount via PayPal"
    }
}

class PixPayment implements Payment {
    processPayment(amount) {
        print "Processando $amount via PIX"
    }
}

// Criador (Factory)
abstract class PaymentFactory {
    // Factory Method
    abstract createPayment(): Payment
    
    // Template Method que usa Factory Method
    processOrder(amount) {
        payment = createPayment()
        payment.processPayment(amount)
    }
}

// Criadores Concretos
class CreditCardFactory extends PaymentFactory {
    createPayment(): Payment {
        return new CreditCardPayment()
    }
}

class PixFactory extends PaymentFactory {
    createPayment(): Payment {
        return new PixPayment()
    }
}

// Uso
factory = new CreditCardFactory()
factory.processOrder(100.00)
// Output: "Processando 100.00 via Cartão de Crédito"

factory = new PixFactory()
factory.processOrder(50.00)
// Output: "Processando 50.00 via PIX"

Padrão Singleton (Instância Única)

Padrão Criacional #2

🔒

Garante que uma classe tenha APENAS UMA INSTÂNCIA e fornece um PONTO DE ACESSO GLOBAL a ela.

Conceito-Chave

Uma classe, uma instância, para sempre!

Problema que Resolve

Quando você precisa controlar acesso a recurso compartilhado (banco de dados, configuração, log)

Características
  • Construtor PRIVADO (ninguém pode fazer 'new')
  • Instância ESTÁTICA (única na memória)
  • Método ESTÁTICO de acesso (getInstance())

Analogias do Mundo Real

🏛️

PRESIDENTE DE UM PAÍS

  • Só pode haver UM presidente por vez
  • Todos acessam o MESMO presidente
  • Não faz sentido ter 2 presidentes simultâneos
⚡

GERENTE DE ENERGIA ELÉTRICA

  • Sistema tem UM gerenciador de energia
  • Todos os componentes consultam o MESMO gerenciador
  • Se tivesse múltiplos gerenciadores = caos
📄

ARQUIVO DE CONFIGURAÇÃO

  • Sistema carrega configurações UMA vez
  • Todas as partes do sistema leem a MESMA configuração
  • Não faz sentido carregar 100x o mesmo arquivo

Estrutura do Singleton

SINGLETON

- static instance: Singleton
- constructor() {private}

+ static getInstance(): Singleton {
    if (instance == null)
        instance = new Singleton()
    return instance
}
+ someMethod(): void
Fluxo Visual
1

Cliente chama Singleton.getInstance()

↓
2

Se instância não existe, cria

↓
3

Se já existe, retorna a existente

↓
4

SEMPRE retorna a MESMA instância

Exemplo Prático: Database Connection

class DatabaseConnection {
    // Instância única (privada e estática)
    private static instance: DatabaseConnection = null
    private connection: Connection
    
    // Construtor PRIVADO (ninguém pode fazer 'new')
    private constructor() {
        // Conecta ao banco (operação cara)
        this.connection = connectToDatabase("localhost", "mydb")
        print "Conexão com banco estabelecida"
    }
    
    // Método público estático para obter instância
    public static getInstance(): DatabaseConnection {
        if (instance == null) {
            instance = new DatabaseConnection()
        }
        return instance
    }
    
    // Métodos de negócio
    public query(sql: string) {
        return this.connection.execute(sql)
    }
}

// Uso
// IMPOSSÍVEL fazer isso (construtor privado):
// db = new DatabaseConnection()  // ERRO!

// Jeito CORRETO:
db1 = DatabaseConnection.getInstance()
db1.query("SELECT * FROM users")

db2 = DatabaseConnection.getInstance()
db2.query("SELECT * FROM orders")

// db1 e db2 são a MESMA instância!
print(db1 === db2)  // true

// Conexão foi estabelecida apenas UMA vez
// Economia de recursos!

Quando Usar Singleton?

🗄️

CONEXÃO COM BANCO DE DADOS

Por quê? Conexões são caras e limitadas

Singleton garante: Uma única conexão reutilizada

📝

SISTEMA DE LOGS

Por quê? Logs precisam ser consistentes e centralizados

Singleton garante: Todos escrevem no mesmo arquivo/sistema

⚙️

CONFIGURAÇÕES GLOBAIS

Por quê? Carregar config múltiplas vezes é desperdício

Singleton garante: Carrega UMA vez, todos usam

💾

GERENCIADOR DE CACHE

Por quê? Cache deve ser compartilhado por toda aplicação

Singleton garante: Uma única fonte de verdade

🔐

CONTROLE DE RECURSOS LIMITADOS

Por quê? Ex: Pool de threads, File handlers

Singleton garante: Controle centralizado

⚠️ CUIDADO:

Singleton pode dificultar testes e criar dependências globais. Use com moderação!

Resolução Exemplo da Atividade 3

CENÁRIO ESCOLHIDO: Gerenciamento de Configuração de uma Aplicação Web

1. Cenário:

"Uma aplicação web de e-commerce precisa carregar configurações globais no início (URL do banco, credenciais de API de pagamento, tempo de sessão, etc.). Essas configurações são lidas de um arquivo config.json na inicialização."

2. O que o Singleton garante:

  • Apenas UMA leitura do arquivo (ao iniciar app)
  • UMA instância de ConfigManager para toda aplicação
  • Todas as partes do sistema acessam a MESMA configuração
  • Não há risco de configurações diferentes em partes diferentes

3. Por que é crucial:

SEM Singleton: Cada requisição HTTP poderia criar uma nova instância de ConfigManager, lendo o arquivo config.json repetidamente. Com 1000 requisições/segundo, teríamos:

  • 1000 leituras de arquivo por segundo (I/O caro)
  • Possibilidade de configurações inconsistentes
  • Desperdício de memória (1000 objetos idênticos)

COM Singleton:

  • 1 leitura de arquivo na inicialização
  • Configurações sempre consistentes
  • Economia de memória e processamento
  • Performance melhorada dramaticamente

Critérios de Avaliação

  • Cenário claro e diferente dos exemplos
  • Explicou o que Singleton garante
  • Justificou por que a garantia é crucial
  • Usou argumentos técnicos (performance, consistência, economia)
