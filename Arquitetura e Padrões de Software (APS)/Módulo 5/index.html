O que é Refatoração?

Melhoria Interna sem Mudar o Comportamento Externo

🔄

Refatoração é o processo de REESTRUTURAR o código existente SEM alterar sua FUNCIONALIDADE EXTERNA (o que o usuário vê e experimenta).

💡 Conceito-Chave

Mudamos a ESTRUTURA INTERNA mantendo o COMPORTAMENTO EXTERNO igual

✅ Benefícios da Refatoração
📖

Código mais LEGÍVEL

Fácil de entender e ler

🔧

Código mais MANUTENÍVEL

Fácil de corrigir e modificar

🚀

Código mais EXTENSÍVEL

Fácil adicionar novas features

  • Reduz complexidade do código
  • Facilita adicionar novas features
  • Melhora a qualidade geral do sistema

Analogia: Organizar uma Casa 🏠

❌ SEM Refatoração
🏚️

Casa Desorganizada

  • 📦 Móveis bagunçados
  • 👕 Roupas espalhadas
  • 🔍 Difícil encontrar as coisas
  • 🧹 Difícil limpar
  • 😰 Visitantes: "Que bagunça!"
✅ COM Refatoração
🏡

Casa Organizada

  • ✨ Móveis no lugar certo
  • 📁 Tudo organizado
  • 👌 Fácil encontrar as coisas
  • 🧽 Fácil limpar
  • 😊 Visitantes: "Que casa bonita!"

🔑 Importante:

A CASA (comportamento externo) continua a mesma. O que mudou foi a ORGANIZAÇÃO INTERNA!

📌 Conclusão: Refatoração é como ORGANIZAR A CASA: você muda móveis de lugar e limpa sem alterar o EXTERIOR da casa. Para quem olha de fora, a casa é a mesma. Mas para quem vive nela, tudo fica mais fácil!

Exemplos de Refatoração

Técnicas Comuns de Refatoração

💡

1. Renomear Variáveis

❌ Antes:

let x = 10

✅ Depois:

let quantidadeProdutos = 10

Por quê: Clareza e legibilidade

📦

2. Extrair Método

❌ Antes:

Método com 100 linhas

✅ Depois:

Método principal + 5 métodos auxiliares

Por quê: Responsabilidade única, legibilidade

♻️

3. Remover Código Duplicado

❌ Antes:

Mesmo código em 3 lugares

✅ Depois:

Código em 1 lugar, chamado 3 vezes

Por quê: DRY (Don't Repeat Yourself)

🔀

4. Simplificar Condicionais

❌ Antes:

if/else aninhados complexos

✅ Depois:

Condicionais simples e claras

Por quê: Reduzir complexidade cognitiva

🔪

5. Dividir Classe Grande

❌ Antes:

Classe com 10 responsabilidades

✅ Depois:

10 classes, cada uma com 1 responsabilidade

Por quê: Single Responsibility Principle

Dívida Técnica: O Atalho que Cobra Juros

💳

Dívida Técnica é o ATALHO de código que prioriza a ENTREGA RÁPIDA hoje, mas que cria CUSTOS de manutenção e desenvolvimento no FUTURO.

🏛️ Origem do Termo

Termo criado por Ward Cunningham (1992), popularizado por Martin Fowler

💡 A Analogia Financeira

Assim como um empréstimo bancário:

  • Valor Principal: Código com atalhos/gambiarras
  • Vantagem Imediata: Feature entregue rapidamente
  • Juros: Tempo extra para manutenção e correções
  • Se não "pagar": Código fica cada vez mais difícil de manter

⚠️ Lembre-se: Dívida Técnica não é necessariamente ruim, mas deve ser gerenciada estrategicamente!

Analogia: Empréstimo Bancário 💳

Aspecto Empréstimo Financeiro Dívida Técnica
Principal Valor emprestado Código com atalhos/gambiarras
Vantagem Imediata Dinheiro na mão hoje Feature entregue rápido
Custo Futuro Juros mensais Manutenção difícil, bugs
Se não pagar Juros aumentam, dívida cresce Código fica insuportável
Pagamento Parcelas + juros Refatoração + tempo extra

💰 Exemplo Financeiro

Você precisa de R$ 10.000 HOJE para uma oportunidade. Pega empréstimo. MAS: paga R$ 15.000 no total (juros de 50%).

💻 Exemplo Técnico

Você precisa entregar feature HOJE. Faz com código ruim. MAS: gasta 3x mais tempo para manter/estender depois.

Tipos de Dívida Técnica

Quadrante de Martin Fowler

✅ Deliberada e Prudente

"Sabemos das consequências mas precisamos entregar agora. Refatoraremos depois."

Exemplo: MVP com prazo apertado, mas com plano de melhoria

Status: ACEITÁVEL (se paga depois)

⚠️ Deliberada e Imprudente

"Não temos tempo para design!"

Exemplo: Sempre priorizar velocidade sobre qualidade

Status: PERIGOSO

💡 Inadvertida e Prudente

"Agora sabemos como deveríamos ter feito."

Exemplo: Aprendizado ao longo do projeto

Status: NORMAL (aprendizado)

❌ Inadvertida e Imprudente

"O que é design?"

Exemplo: Falta de conhecimento técnico

Status: CRÍTICO

Princípios SOLID: Os 5 Pilares do Código Limpo

🏛️

SOLID é um acrônimo de 5 princípios de design orientado a objetos que tornam o software mais compreensível, flexível e manutenível.

👨‍💻 Criador

Criados por Robert C. Martin ('Uncle Bob') em 2000

Os 5 Princípios SOLID
S

Single Responsibility Principle (SRP)

Princípio da Responsabilidade Única

O

Open/Closed Principle (OCP)

Princípio Aberto/Fechado

L

Liskov Substitution Principle (LSP)

Princípio da Substituição de Liskov

I

Interface Segregation Principle (ISP)

Princípio da Segregação de Interface

D

Dependency Inversion Principle (DIP)

Princípio da Inversão de Dependência

⭐ Foco deste módulo: Estudaremos em detalhes o PRIMEIRO princípio: SRP (Single Responsibility Principle)

Single Responsibility Principle (SRP)

Princípio da Responsabilidade Única

🎯

Uma classe deve ter APENAS UMA RAZÃO para mudar. Em outras palavras: uma classe deve ter APENAS UMA RESPONSABILIDADE.

💬 Uncle Bob diz:

"Gather together the things that change for the same reasons. Separate those things that change for different reasons."

- Robert C. Martin

🔑 Conceito-Chave

RESPONSABILIDADE = RAZÃO PARA MUDAR = ATOR QUE SOLICITA MUDANÇA

💡 Em outras palavras: Se você pode pensar em mais de uma razão para modificar uma classe, então ela tem mais de uma responsabilidade.

Entendendo "Responsabilidade" no SRP

"Responsabilidade" deve ser vista como um EIXO DE MUDANÇA. Se a classe muda quando a regra de NEGÓCIO muda E também muda quando a regra de LOG muda, ela VIOLA o SRP.

❌ Classe que VIOLA SRP
class Usuario {
    criarUsuario()        // Muda quando: Regra de negócio muda
    validarEmail()        // Muda quando: Regra de validação muda
    salvarNoBanco()       // Muda quando: Banco de dados muda
    enviarEmailBoasVindas() // Muda quando: Template de email muda
    gerarRelatorio()      // Muda quando: Formato do relatório muda
}

❌ 5 RAZÕES PARA MUDAR = VIOLA SRP!

  • Mudança na regra de negócio → Modifica a classe
  • Mudança na validação → Modifica a classe
  • Mudança no banco de dados → Modifica a classe
  • Mudança no template de email → Modifica a classe
  • Mudança no relatório → Modifica a classe
✅ Respeitando SRP
Usuario: Regras de negócio
EmailValidator: Validação
UsuarioRepository: Persistência
EmailService: Envio de emails
RelatorioService: Geração de relatórios

✅ Cada classe tem 1 RAZÃO para mudar

Analogia: Especialista vs Multifuncional 👨‍💼

❌ Profissional MULTIFUNCIONAL
😰

João faz TUDO

  • 📊 Contador
  • 🎨 Designer
  • 💻 Programador
  • 💼 Vendedor

✗ Quando contabilidade muda → João muda

✗ Quando design muda → João muda

✗ Quando código muda → João muda

✗ Quando vendas mudam → João muda

😩 João sobrecarregado, mudanças arriscadas

✅ Profissionais ESPECIALISTAS
😊

Cada um com SUA área

  • 📊 Maria: Contadora (só cuida de finanças)
  • 🎨 Pedro: Designer (só cuida de design)
  • 💻 Ana: Programadora (só cuida de código)
  • 💼 Lucas: Vendedor (só cuida de vendas)

✓ Mudança em finanças → Só Maria trabalha

✓ Mudança em design → Só Pedro trabalha

✓ Mudança em código → Só Ana trabalha

✓ Mudança em vendas → Só Lucas trabalha

😊 Cada um especialista, mudanças isoladas

📌 Conclusão: Especialistas (classes com 1 responsabilidade) são mais eficientes e menos arriscados do que multifuncionais (classes com N responsabilidades)!

Por Que Seguir o SRP?

5 Principais Benefícios

🔧

1. Manutenibilidade

  • Mudanças localizadas
  • Fácil encontrar onde mudar
  • Menos risco de quebrar código
✅

2. Testabilidade

  • Classes pequenas = testes simples
  • Mock de dependências facilitado
  • Cobertura de testes maior
♻️

3. Reusabilidade

  • Classes com 1 responsabilidade podem ser reutilizadas
  • Menos acoplamento
  • Composição facilitada
📖

4. Compreensibilidade

  • Código mais fácil de entender
  • Nome da classe = sua responsabilidade
  • Onboarding mais rápido
🚀

5. Evolução

  • Fácil adicionar novas features
  • Fácil substituir implementações
  • Arquitetura flexível

Como Saber se Estou Violando o SRP?

Sinais de Alerta (Red Flags)

🚩

Classe com nome genérico

Exemplos: Manager, Handler, Util, Helper

Indica: Responsabilidades mal definidas

🚩

Classe muito grande

Métrica: > 200-300 linhas

Indica: Múltiplas responsabilidades

🚩

Métodos que não se relacionam

Exemplo: Classe tem calcularImposto() E enviarEmail()

Indica: Responsabilidades diferentes

🚩

Muitas razões para mudar

Mudança em LOG afeta classe
Mudança em BANCO afeta classe
Mudança em NEGÓCIO afeta classe

Indica: Viola SRP

🚩

Difícil dar nome para a classe

Classe faz X, Y, Z e W
Precisa de "E" ou "Ou" no nome

Indica: Responsabilidades não coesas

Exemplo: Classe que VIOLA SRP

class GerenciadorUsuario {
    // Responsabilidade 1: Gerenciar dados do usuário
    criarUsuario(nome, email) {
        validarDados(nome, email)
        usuario = new Usuario(nome, email)
        return usuario
    }
    
    atualizarUsuario(id, nome, email) {
        usuario = buscarUsuario(id)
        usuario.nome = nome
        usuario.email = email
        salvarUsuario(usuario)
    }
    
    // Responsabilidade 2: Persistência no banco
    salvarUsuario(usuario) {
        sql = "INSERT INTO usuarios..."
        database.execute(sql)
    }
    
    buscarUsuario(id) {
        sql = "SELECT * FROM usuarios WHERE id = " + id
        return database.query(sql)
    }
    
    // Responsabilidade 3: Validação
    validarDados(nome, email) {
        if (nome.length < 3)
            throw "Nome inválido"
        if (!email.contains("@"))
            throw "Email inválido"
    }
    
    // Responsabilidade 4: Envio de emails
    enviarEmailBoasVindas(usuario) {
        assunto = "Bem-vindo!"
        corpo = "Olá " + usuario.nome + "..."
        emailService.send(usuario.email, assunto, corpo)
    }
    
    // Responsabilidade 5: Relatórios
    gerarRelatorioUsuarios() {
        usuarios = buscarTodosUsuarios()
        relatorio = formatarRelatorio(usuarios)
        return relatorio
    }
}

❌ Problemas Identificados:

  • 5 responsabilidades diferentes na mesma classe
  • 5 razões para mudar esta classe
  • VIOLA SRP!

Refatoração: Respeitando o SRP

// Responsabilidade ÚNICA: Gerenciar regras de negócio de usuário
class UsuarioService {
    constructor(repository, validator, emailService) {
        this.repository = repository
        this.validator = validator
        this.emailService = emailService
    }
    
    criarUsuario(nome, email) {
        this.validator.validar(nome, email)
        usuario = new Usuario(nome, email)
        this.repository.salvar(usuario)
        this.emailService.enviarBoasVindas(usuario)
        return usuario
    }
    
    atualizarUsuario(id, nome, email) {
        this.validator.validar(nome, email)
        usuario = this.repository.buscar(id)
        usuario.nome = nome
        usuario.email = email
        this.repository.salvar(usuario)
    }
}

// Responsabilidade ÚNICA: Persistência
class UsuarioRepository {
    salvar(usuario) {
        sql = "INSERT INTO usuarios..."
        database.execute(sql)
    }
    
    buscar(id) {
        sql = "SELECT * FROM usuarios WHERE id = " + id
        return database.query(sql)
    }
}

// Responsabilidade ÚNICA: Validação
class UsuarioValidator {
    validar(nome, email) {
        if (nome.length < 3)
            throw "Nome inválido"
        if (!email.contains("@"))
            throw "Email inválido"
    }
}

// Responsabilidade ÚNICA: Email
class EmailService {
    enviarBoasVindas(usuario) {
        assunto = "Bem-vindo!"
        corpo = "Olá " + usuario.nome + "..."
        this.send(usuario.email, assunto, corpo)
    }
}

// Responsabilidade ÚNICA: Relatórios
class RelatorioService {
    gerarRelatorioUsuarios() {
        usuarios = repository.buscarTodos()
        return this.formatarRelatorio(usuarios)
    }
}

✅ Resultado: 5 classes, cada uma com 1 responsabilidade. Cada classe tem 1 razão para mudar. RESPEITA SRP!

🎮 Atividade: Esta Classe Viola o SRP?

📋 Analise o código abaixo:

class Produto {
    nome: string
    preco: number
    
    calcularPrecoComDesconto(percentual) {
        return this.preco * (1 - percentual/100)
    }
    
    salvarNoBanco() {
        sql = "INSERT INTO produtos..."
        database.execute(sql)
    }
    
    enviarEmailPromocao(email) {
        assunto = "Promoção: " + this.nome
        emailService.send(email, assunto, this.preco)
    }
}

❓ Esta classe Produto viola o SRP?

Resumo: Single Responsibility Principle

📖 Definição

Uma classe deve ter APENAS UMA RAZÃO para mudar

🔍 Como Identificar Violação

  • Classe muito grande
  • Métodos não relacionados
  • Múltiplas razões para mudar
  • Nome genérico (Manager, Helper, Util)

🛠️ Como Aplicar

  • Separar responsabilidades em classes diferentes
  • Cada classe = 1 responsabilidade
  • Coesão alta dentro da classe
  • Acoplamento baixo entre classes

✅ Benefícios

  • ✓ Código mais legível
  • ✓ Mais fácil de testar
  • ✓ Mais fácil de manter
  • ✓ Mais fácil de estender

ATIVIDADE 5 (APS) - Análise e Aplicação do SRP

Problema

📋 Cenário:

Imagine uma classe chamada GerenciadorProduto que possui os seguintes métodos:

    CriarProduto(nome, preco)

}

❓ Questões:

1. Essa classe viola o Princípio da Responsabilidade Única (SRP)? Se sim, por quê?

2. Sugira a refatoração, dividindo essa classe em novas classes que respeitem o SRP. Liste os novos nomes e suas responsabilidades.

ATIVIDADE 5: Resolução Comentada - Análise

1. Essa classe viola o SRP?

✅

SIM, VIOLA O SRP!

📊 Análise das Responsabilidades
Responsabilidade 1: Gerenciamento de Produtos

Métodos: CriarProduto(), AtualizarProduto()

Razão para mudar: Regras de negócio de produtos mudam

Ator: Gerente de produtos / Equipe de negócios

Responsabilidade 2: Comunicação (Email Marketing)

Método: EnviarEmailPromocional()

Razão para mudar: Template de email muda, estratégia de marketing muda

Ator: Equipe de marketing

Responsabilidade 3: Geração de Relatórios

Método: GerarRelatorioVendas()

Razão para mudar: Formato do relatório muda, métricas mudam

Ator: Equipe de Business Intelligence / Gerência

❌ Por que VIOLA o SRP:

A classe tem 3-4 RAZÕES DIFERENTES para mudar. Se a equipe de marketing decide mudar o template de email promocional, a classe GerenciadorProduto precisa ser alterada. Se o BI quer novo formato de relatório, a classe também muda. Isso cria ACOPLAMENTO entre responsabilidades não relacionadas e AUMENTA o risco de bugs.

ATIVIDADE 5: Resolução Comentada - Refatoração

2. Proposta de Refatoração

📦

Classe 1: ProdutoService

Responsabilidade: Gerenciar REGRAS DE NEGÓCIO de produtos

Métodos:

  • CriarProduto(nome, preco)
  • AtualizarProduto(id, nome, preco)
  • BuscarProduto(id)

Razão única para mudar: Regras de negócio de produtos mudam

📧

Classe 2: EmailMarketingService

Responsabilidade: Gerenciar ENVIO DE EMAILS PROMOCIONAIS

Métodos:

  • EnviarEmailPromocional(produto, listaEmails)
  • EnviarCampanha(campanha)

Razão única para mudar: Estratégia de marketing ou templates de email mudam

📊

Classe 3: RelatorioVendasService

Responsabilidade: Gerenciar GERAÇÃO DE RELATÓRIOS de vendas

Métodos:

  • GerarRelatorioVendas(periodo)
  • GerarRelatorioMensal()
  • ExportarParaPDF(relatorio)

Razão única para mudar: Formato ou métricas dos relatórios mudam

✅ Agora cada classe tem APENAS UMA responsabilidade e APENAS UMA razão para mudar. O código fica mais organizado, testável e manutenível!
